# Интеграции Pulse с Windows

## Что подтверждено по файлам

| Приложенный файл | Метаданные PE | SHA-256 |
| --- | --- | --- |
| `Pulse.exe` | Pulse от exepcstudio, `OriginalFilename=Pulse.exe`, версия 1.4.0.0 | `A25F33E71364BE8CC1E6FAE56210D4A354F87D1ADF29752562667513FCCF4005` |
| `Pulse-Update-2.exe` | Pulse Updater, `OriginalFilename=Pulse-Update.exe`, версия 1.0.0.0, пустое поле CompanyName | `572A18BD452ADC0E78EC0BF860F3D0B6868869A0889FC7A806D4A6353E16547E` |

Метаданные проверены через `FileVersionInfo`, SHA-256 через `Get-FileHash`. Статическое чтение IL приложенного `Pulse.exe` в режиме ReflectionOnly подтвердило следующее.

- `Pulse.Setup.DefaultInstallDir` выбирает `Pulse` на подходящем фиксированном томе и содержит запасной путь `%LOCALAPPDATA%\Programs\Pulse`.
- `Pulse.Setup.Install` использует `Pulse.lnk`, ключ `Software\Microsoft\Windows\CurrentVersion\Uninstall\exepcstudio.Pulse` и поля `Publisher`, `DisplayIcon`, `InstallLocation` и `UninstallString`. Штатная строка удаления указывает на EXE с аргументом `--uninstall`.
- `Pulse.Setup.SetAutostart` использует значение `Pulse` в `Software\Microsoft\Windows\CurrentVersion\Run` и аргумент `--hidden`.
- Исходники предшествующего updater в `2026-11-20/Pulse/updater/Product.cs` ищут те же ключи и прямые цели ярлыков. `Install.cs` и `build.ps1` подтверждают имя вложенного ресурса `Pulse.Fixed.exe`. Создание особых служб или задач Pulse по этим файлам не установлено.

## Границы обнаружения и удаления

- Кандидатов дают стандартные пути, прямые цели найденных сочетаний реестра, ярлыков, задач и служб, а также пути образов работающих процессов. Метаданные позволяют обнаружить побайтно неизменённый EXE под другим именем. Основание для плана и удаления даёт разрешённый SHA-256 и повторная проверка файла.
- Реестр проверяется в `HKCU`, `HKLM` и доступных загруженных пользовательских ветвях `HKEY_USERS`. На 64-битной Windows проверяются оба представления. В область входят `Run`, `RunOnce` и проверяемые записи удаления. Незагруженные ветви профилей и недоступные области отражаются в отчёте. Доступные файлы таких профилей проверяются по известным путям.
- Очиститель читает прямые локальные цели `.lnk` на рабочем столе, в меню «Пуск» и в автозагрузке. Он повторно проверяет идентификатор, атрибуты и SHA-256 ярлыка перед удалением через открытый файловый дескриптор. Перенаправления, облачные объекты и удалённые цели пропускаются. [Документация IShellLinkW::GetPath](https://learn.microsoft.com/en-us/windows/win32/api/shobjidl_core/nf-shobjidl_core-ishelllinkw-getpath)
- Для задачи каждое действие должно иметь прямую подтверждённую цель `Exec`. Для Win32-службы с собственным процессом требуется прямая подтверждённая цель, проверенная конфигурация SCM и совпадение активного образа перед остановкой. Команды и аргументы из записей используются как данные. Смешанные задачи, общие хосты служб и косвенные цели остаются для проверки. Если заведомо принадлежащую Pulse запись нельзя удалить, связанный EXE сохраняется как основание повторного поиска. [Действия задач](https://learn.microsoft.com/en-us/windows/win32/taskschd/task-actions), [конфигурация службы](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-queryserviceconfigw), [статус службы](https://learn.microsoft.com/en-us/windows/win32/api/winsvc/nf-winsvc-queryservicestatusex)
- После обработки автозапуска процессы проверяются повторным снимком, PID, временем создания, путём и содержимым образа. Для Pulse сначала запрашивается штатное закрытие окна. Принудительное завершение использует дескриптор перепроверенного процесса. Для WebView2 дополнительно требуются подтверждённая родительская цепочка в той же сессии, метаданные образа и выделенный профиль. Профиль сверяется по `--user-data-dir`. Общий профиль или пропавшие сведения о происхождении процесса оставляют WebView2 вне удаления. Известный профиль занятого WebView2 помечается в отчёте для повторной попытки. [Синтаксис прямой цели CreateProcessW](https://learn.microsoft.com/en-us/windows/win32/api/processthreadsapi/nf-processthreadsapi-createprocessw)
- Смена записи обнаруживается повторной проверкой непосредственно перед удалением. Обычные API реестра и планировщика оставляют окно для внешнего изменения между последней проверкой и удалением по имени. Копии за пределами доступных стандартных и выбранных каталогов остаются за пределами этого поиска.

## Локальные проверки

| Статус | Проверка и предел |
| --- | --- |
| PASS | Статическая проверка обоих приложенных EXE, метаданных, хэшей и строк установочных методов оболочки. |
| PASS | Компиляция исходников полноценного очистителя с `/warnaserror+` через `cleanup/build.ps1` в отдельный временный каталог. Полученный EXE не запускался. |
| PASS | Сборка `TEST_FIXTURES` и запуск только `--integration-unit` завершились с кодом 0. Данные тестов покрывают точные и неоднозначные цели, косвенные команды, смешанные действия и XML задач, подмену файла после запуска, повторный PID, другую сессию и неподтверждённого родителя WebView2. |
| BLOCKED | Локальная проверка изменений реестра, ярлыков, задач, служб и процессов требует отдельной Windows VM. На рабочем компьютере эти операции не выполнялись. |

## Диагностика прогона Windows Server 2025

- Первый прогон подтвердил удаление записей реестра, ярлыка, службы, приложения и старого updater. Проверки задачи и WebView2 завершились составным FAIL. Повторный прогон того же EXE с расширенным журналом подтвердил штатное удаление задачи и сохранность контрольной задачи. Строка об удалении отсутствовала. [Первый прогон](https://github.com/mrfrog2029-boop/pulse-windows-qa-2026-11-21/actions/runs/44897043304), [диагностический прогон](https://github.com/mrfrog2029-boop/pulse-windows-qa-2026-11-21/actions/runs/44897674877)
- Вызов `GetTask` для заведомо отсутствующего синтетического имени в .NET Framework воспроизвёл `System.IO.FileNotFoundException` с HRESULT `80070002`. Обработчик ожидал только `COMException`, поэтому подтверждение успешного удаления терялось при контрольном чтении. Теперь проверка учитывает оба представления ошибки. Отказ в доступе остаётся ошибкой. Регрессионный тест с прежним условием воспроизвёл дефект распознавания и прошёл с новым условием.
- В диагностическом прогоне наблюдался один дочерний WebView2. PID исчез после очистки и отсутствовал в отчёте. Очиститель теперь удерживает перепроверенный дескриптор дочернего процесса до закрытия Pulse и записывает естественное завершение только по сигналу этого дескриптора. Принудительное завершение по-прежнему требует подтверждённого частного профиля.
- Стандартный файловый предохранитель воспроизводимо отклонил штатный `msedgewebview2.exe` версии 157.0.4341.60 с двумя жёсткими ссылками. Ограниченное открытие метаданных подтвердило обе ссылки и имя продукта. Оно доступно для чтения образа runtime. Для записи и удаления файлов остаются прежние проверки. Третий прогон исходного EXE подтвердил две жёсткие ссылки и точный непосредственный каталог `Data\WebView\EBWebView` на Windows Server 2025 с WebView2 157.0.4341.46 и Windows Server 2022 с WebView2 131.0.2903.86. В проверку принадлежности теперь входят подтверждённый внешний каталог API и его непосредственный каталог `EBWebView`. [Проверка путей и контрольного WebView2](https://github.com/mrfrog2029-boop/pulse-windows-qa-2026-11-21/actions/runs/44898182655), [совместное использование файлов Evergreen WebView2](https://learn.microsoft.com/en-us/microsoft-edge/webview2/concepts/distribution)
